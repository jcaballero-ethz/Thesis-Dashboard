## Overview

This project identifies, characterizes, and clusters **weather-driven stress events** in the European energy system using two 60-scenario climate ensembles (future and historical) modelled with the **ZEN-garden** linear programming energy model.

### What is a stress event?

A stress event is a continuous time interval during which the energy system is under high cost pressure, identified through a shadow-price-based stress indicator applied globally across the full climate ensemble.

**Step 1 — Stress indicator.** For each timestep `t` and climate scenario `s`, a timestep-level stress cost is computed as:

```
Φ_{t,s} = Σ_{n ∈ N} Σ_{c ∈ C}  d_{c,n,t,s} · λ_{c,n,t,s}
```

where:
- `d_{c,n,t,s}` — demand of carrier `c` at node `n`, hour `t`, scenario `s` (GWh)
- `λ_{c,n,t,s}` — shadow price of the nodal energy balance constraint for carrier `c` at node `n`, hour `t`, scenario `s` (M€/GWh)
- The sum runs over all nodes `N` and all modeled energy carriers `C`

`Φ_{t,s}` is a shadow-price-weighted demand indicator: it measures how much of the total demand is served under high marginal system-cost conditions at a given timestep and scenario.

**Step 2 — Global cross-scenario selection.** All `|T| × |Ω|` timestep–scenario pairs are pooled into a single global set and ranked in descending order of `Φ_{t,s}`. Starting from the highest-ranked pair, pairs are added sequentially to the selected set `S_α` until their cumulative stress cost covers a fraction α of the total cross-scenario stress cost `Φ_tot`:

```
Σ_{(t,s) ∈ S_α} Φ_{t,s}  ≥  α · Φ_tot
```

`α` is thus a **cost-coverage parameter**: it controls what fraction of the total ensemble stress cost is represented by the selected timestep–scenario pairs. It is not a percentile threshold.

**Step 3 — Event construction.** Within each scenario, the selected timesteps are ordered chronologically. Consecutive selected timesteps separated by at most `τ_gap = 48 h` are merged into one event. The event spans the full continuous interval from its first to its last selected timestep (including any intermediate non-selected hours).

**Step 4 — Filtering.** Candidate events are retained only if they satisfy both:
- `cost_share_cross ≥ 0.2%` — the event's cumulative stress cost is at least 0.2% of `Φ_tot`
- `duration ≥ 1 day`

This yields 40 retained events (future) and 42 (historical) at α = 25%.

### The two datasets

| Dataset | ZEN-garden folder |
|---------|-------------------|
| **Future** | `20260202_GF_future_with_cooling` |
| **Historical** | `20260202_GF_historical_with_cooling` |

Each dataset contains 60 scenarios (`scenario_1` … `scenario_60`), each representing one year (8760 hours) under a different climate realization. The energy system infrastructure (capacities, topology) is the same across all scenarios within a dataset; only the weather-driven inputs (wind, solar, demand) vary.

## CSVs and JSONs — what they contain

All commands in the pipeline below are run from the **repository root** (`~/Desktop/Bachelor Thesis/`).

### `CSVs_and_JSONs/{future|historical}/events_global_alpha/events_global_alpha{XX}.csv`

One file per α threshold (10, 15, 20, 25, 30, 35, 40). Each row is one stress event.

| Column | Description |
|--------|-------------|
| `rank` | Ranking by event cost (1 = most expensive) |
| `sc` | Scenario number (0–59) |
| `t_start` | First hour of the event (0–8759) |
| `t_end` | Last hour of the event (0–8759) |
| `duration_days` | Event duration in days |
| `event_cost` | Total Φ summed over the event hours (M€) |
| `cost_share_cross` | Event cost as a fraction of total cost across all scenarios (%) |

### `CSVs_and_JSONs/{future|historical}/features/features_alpha25_climate_{future|historical}_clustered.csv`

Climate feature table for events at α = 25%, after clustering. One row per event. Features are **anomalies relative to the scenario annual mean**, averaged over the event hours.

| Column group | Description |
|--------------|-------------|
| `wind anom {zone}` | Wind capacity factor anomaly (percentage points) for each of the 13 geographic zones |
| `pv anom {zone}` | PV capacity factor anomaly (percentage points) |
| `heat anom {zone}` | Heat demand anomaly (percentage points) |
| `sc`, `t_start`, `t_end` | Event identifier |
| `cluster_climate` | Climate cluster label (1–4) assigned by K-Medoids |

The 13 zones are defined by Ward hierarchical clustering of country-level wind anomaly correlations at a threshold r ≥ 0.65: Nordics_N, Nordics_S, Baltics, British_Isles, NW_Continent, Central_W, Central_E, East_N, Iberia, Med_East_N, Med_East_S, Italy, Greece.

### `CSVs_and_JSONs/{future|historical}/features/features_alpha25_operational_{future|historical}_clustered.csv`

Operational feature table for events at α = 25%. Same structure as the climate table but features include:
- `wind anom`, `pv anom`, `heat anom` per zone (same as climate table)
- `nettrans anom {zone}` — net transmission import anomaly (GWh/h) for each zone
- `stor_diff` — pan-European storage level difference between end and start of event (GWh)
- `stor_rate` — average net storage discharge rate during the event (GWh/h)
- `cluster_operational` — operational cluster label (1–4)

### `CSVs_and_JSONs/{future|historical}/features/features_alpha25_{future|historical}_per_country.csv`

Per-country feature table used for correlation analysis (zone definition). One row per event, one column group per country (27 countries). Columns per country:
- `wind anom {CC}`, `pv anom {CC}`, `heat anom {CC}` — anomalies (percentage points)
- `ngt {CC}` — net generation transport
- `stor rate {CC}`, `stor diff {CC}` — storage metrics

## ZEN-garden API — quick reference

ZEN-garden is a linear programming energy system model. Scripts access its outputs via:

```python
from zen_garden import Results
r = Results(path='path/to/output/folder')

# Time series (returns DataFrame: index = (technology/carrier, node), columns = hours 0..8759)
r.get_full_ts('flow_conversion_output', scenario_name='scenario_3')  # GWh/h
r.get_full_ts('demand',                 scenario_name='scenario_3')  # GWh
r.get_full_ts('max_load',              scenario_name='scenario_3')  # capacity factor [0–1]
r.get_full_ts('flow_transport',        scenario_name='scenario_3')  # GWh/h
r.get_full_ts('storage_level',         scenario_name='scenario_3')  # GWh
r.get_full_ts('flow_storage_discharge',scenario_name='scenario_3')  # GWh/h

# Dual variables (shadow prices)
r.get_dual('constraint_nodal_energy_balance',    scenario_name='scenario_3')  # M€/GWh
r.get_dual('constraint_capacity_factor_transport',scenario_name='scenario_3') # congestion dual
```

### Exploring what variables, parameters, and duals are available

To discover what is available in the model, use `get_component_names`:

```python
import logging
logging.getLogger("pint").setLevel(logging.ERROR)
from zen_garden import Results
import os

r = Results(path=os.path.expanduser(
    '~/Desktop/ZEN-garden model/outputs/20260202_GF_future_with_cooling'))

for category in ('variable', 'parameter', 'dual', 'sets'):
    print(f'\n=== {category.upper()}S ===')
    for name in r.get_component_names(category):
        print(' ', name)
```

Running this on the future dataset produces:

```

  cost_*                 flow_storage_charge      storage_level
                         flow_storage_discharge   ...

  availability_export    demand                   max_load
  capex_*                efficiency_charge        min_load

  conversion_factor      energy_to_power_ratio_*  price_*
  ...

=== DUALS ===
  constraint_availability_export       constraint_nodal_energy_balance

=== SETS ===
  set_dependent_carriers    set_nodes_on_edges       set_reference_carriers
  set_input_carriers        set_output_carriers      set_technologies_existing
```

The most useful ones for this analysis are `flow_conversion_output`, `demand`, `max_load`, `flow_transport`, `storage_level`, `flow_storage_discharge` (variables/parameters) and `constraint_nodal_energy_balance`, `constraint_capacity_factor_transport` (duals).

Once you know the name, inspect its index to see which technologies, carriers, and nodes it covers:

```python
sc = 'scenario_1'

df = r.get_full_ts('flow_conversion_output', scenario_name=sc)
print(df.index.names)                         # e.g. ('technology', 'carrier', 'node')
print(df.index.get_level_values(0).unique())  # all conversion technologies
print(df.index.get_level_values(1).unique())  # all carriers
print(df.index.get_level_values(2).unique())  # all nodes (countries)

# Generic: works for any variable regardless of how many index levels it has
for i, name in enumerate(df.index.names):
    print(f"level {i} ({name}): {df.index.get_level_values(i).unique().tolist()}")

# For dual variables:
dual = r.get_dual('constraint_nodal_energy_balance', scenario_name=sc)
print(dual.index.names)                        # e.g. ('carrier', 'node')
print(dual.index.get_level_values(0).unique()) # carriers with a balance constraint
```

### Other useful methods

```python
# Units and documentation for any component
r.get_unit('flow_conversion_output')   # e.g. 'GWh'
r.get_doc('demand')                    # human-readable description

# Annual aggregated values (instead of full 8760-hour time series)
r.get_total('capacity', scenario_name=sc)

# Targeted filtering without manual index masking
r.get_full_ts('flow_conversion_output', scenario_name=sc,
              index=('wind_onshore', None, ['DE', 'FR']))  # only wind in DE and FR
r.get_total('capacity',
            index={'technology': 'photovoltaics', 'node': 'ES'})
```

## Extending this work

If you want to continue this analysis, here are the most natural next steps:

- **Change α or filtering thresholds:** update the constants at the top of the relevant scripts (see table above) and re-run from Step 1 or Step 2 depending on which threshold you changed.
- **Add a new feature to clustering:** add the feature computation in `compute_clustering_climate.py` or `compute_clustering_operational.py`, re-run from Step 2 onwards.
- **Add a new country or zone:** update the zone definition in the clustering scripts and re-run from Step 2.
- **Add a new HTML visualization:** create a new `generate_*.py` script in `analysis/codigos/generate/`, then add a tab for it in `analysis/htmls_uso/thesis_dashboard.html`.
- **Use a different dataset:** update the `path` entries in the `DATASETS` dict at the top of each compute script, then re-run the full pipeline.
- **Try different clustering algorithms:** the clustering logic is in `compute_clustering_climate.py` and `compute_clustering_operational.py`. The silhouette score loop is already in the script — adapt it to compare algorithms.
